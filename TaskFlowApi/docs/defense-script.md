# Шпаргалка для защиты: безопасность TaskFlow API

## Перед защитой

Запустить проект:

```bash
cd /home/kate/dotnet-lessons/TaskFlowApi
dotnet run
```

Открыть Swagger:

```text
http://localhost:5248/swagger
```

Также открыть следующие файлы:

- `Program.cs` — настройка JWT, ролей, политик и защитных заголовков;

## Начало рассказа

> Моя работа — это REST API для управления задачами. В этой части задания я добавила регистрацию и вход пользователей, JWT-токены, авторизацию по ролям, проверку владельца конкретной задачи и защитные HTTP-заголовки.
>
> Аутентификация отвечает на вопрос «кто пользователь», а авторизация отвечает на вопрос «что этому пользователю разрешено».

## Регистрация и пароль

Открыть `Controllers/AuthController.cs` и показать метод `Register`.

> Пользователь отправляет имя, электронную почту и пароль. Открытый пароль в базе не сохраняется. С помощью `PasswordHasher` создаётся хеш пароля, и в базу записывается только этот хеш.
>
> При обычной регистрации сервер всегда назначает роль `User`. Пользователь не может передать себе роль `Admin`, потому что это было бы небезопасно.

Запрос для демонстрации:

```http
POST http://localhost:5248/api/auth/register
Content-Type: application/json

{
  "username": "student",
  "email": "student-demo@example.com",
  "password": "Secure123!"
}
```

Ожидаемый результат:

```text
201 Created
```

Если пользователь с таким e-mail уже существует, изменить адрес, например на `student-demo2@example.com`.

## Вход и JWT

Открыть метод `Login` в `Controllers/AuthController.cs`.

> При входе сервер находит пользователя и проверяет введённый пароль по сохранённому хешу. Если пароль правильный, сервер создаёт JWT-токен сроком на один час.
>
> В токене находятся ID пользователя, имя, электронная почта и роль. JWT подписан секретным ключом. Его содержимое можно прочитать, но незаметно изменить токен нельзя: после изменения подпись перестанет совпадать.

Запрос:

```http
POST http://localhost:5248/api/auth/login
Content-Type: application/json

{
  "email": "student-demo@example.com",
  "password": "Secure123!"
}
```

Ожидаемый результат:

```text
200 OK
```

Из ответа скопировать значение `accessToken` и вставить в начало `TaskFlowApi.http`:

```http
@token = сюда_вставить_токен
```

## Проверка аутентификации

Сначала выполнить запрос без заголовка `Authorization`:

```http
GET http://localhost:5248/api/auth/me
```

Ожидаемый результат:

```text
401 Unauthorized
```

> Код 401 означает, что сервер не смог определить пользователя: токен отсутствует, просрочен или недействителен.

Теперь выполнить запрос с токеном:

```http
GET http://localhost:5248/api/auth/me
Authorization: Bearer {{token}}
```

Ожидаемый результат:

```text
200 OK
```

> Сервер проверил подпись, издателя, получателя и срок действия токена. После этого он восстановил данные пользователя из claims.

## Проверка роли

Открыть `Program.cs` и показать политику:

```csharp
options.AddPolicy(
    "AuthorOrAdmin",
    policy => policy.RequireRole("Author", "Admin"));
```

> В системе предусмотрены роли `User`, `Author` и `Admin`. Обычный пользователь может читать данные. Создавать проекты и задачи могут `Author` и `Admin`. Удаление разрешено только администратору.

Попробовать создать задачу с токеном пользователя `User`:

```http
POST http://localhost:5248/api/v2/tasks
Authorization: Bearer {{token}}
X-Idempotency-Key: 0133df02-7da1-4e18-a52e-bba715127fc2
Content-Type: application/json

{
  "title": "Проверка безопасности",
  "projectId": 1
}
```

Ожидаемый результат:

```text
403 Forbidden
```

> Код 403 означает, что сервер уже определил пользователя, но у него недостаточно прав. У пользователя роль `User`, а для создания задачи нужна роль `Author` или `Admin`.

## Проверка владельца задачи

Открыть `Authorization/CanEditTaskHandler.cs`.

> Одной проверки роли недостаточно. Например, два пользователя могут иметь роль `Author`, но один автор не должен редактировать задачу другого автора.
>
> Поэтому при создании задачи сервер самостоятельно записывает ID текущего пользователя в `CreatedByUserId`. При редактировании обработчик `CanEditTaskHandler` сравнивает владельца задачи с ID пользователя. Изменить задачу может её автор или администратор.

Короткая формулировка:

> Роль определяет общий уровень доступа, а политика `CanEditTask` проверяет право на конкретную задачу.

## Защитные заголовки

Показать соответствующий middleware в `Program.cs` или выполнить в терминале:

```bash
curl -i http://localhost:5248/api/projects
```

Найти в ответе:

```text
Content-Security-Policy
X-Content-Type-Options
X-Frame-Options
Referrer-Policy
```

> `Content-Security-Policy` ограничивает источники содержимого. `X-Content-Type-Options` запрещает браузеру угадывать тип файла. `X-Frame-Options: DENY` запрещает встраивать приложение в чужой iframe. `Referrer-Policy` ограничивает передачу адреса страницы другим сайтам. В production также включается HSTS, который требует использовать HTTPS.

## Почему нет CSRF-токена

> Это REST API с JWT в заголовке `Authorization`. Браузер не отправляет такой токен автоматически, как cookie. Поэтому классические CSRF-токены для этого варианта аутентификации не используются.
>
> При этом JWT не защищает от всех атак. Если злоумышленник украдёт токен через XSS, он сможет использовать его до окончания срока действия.

## Важное уточнение про ASP.NET Core Identity

> В этом учебном проекте я не подключала полный ASP.NET Core Identity. Я использовала собственную сущность `AppUser` и стандартный `PasswordHasher` из ASP.NET Core. Это упрощённая реализация для демонстрации JWT, ролей и политик. В большом production-проекте лучше использовать полноценный Identity или отдельный проверенный сервис авторизации.

Не говорить: «Я полностью подключила ASP.NET Core Identity».

## Если попросят показать администратора

> Через публичную регистрацию специально нельзя получить роль `Admin`. Иначе любой пользователь смог бы зарегистрироваться администратором. Повышенную роль должен назначать доверенный администратор через закрытую систему управления пользователями.

В текущей демонстрации проще показать отказ `403` для обычного пользователя, а правила `Author` и `Admin` показать в коде.

## Короткие ответы на вопросы

### Чем 401 отличается от 403?

> 401 — пользователь не определён. 403 — пользователь определён, но у него недостаточно прав.

### Можно ли прочитать JWT?

> Да. JWT обычно подписан, но не зашифрован. Поэтому пароли и секретные данные в токен класть нельзя.

### Что произойдёт, если изменить роль в JWT?

> Подпись токена перестанет совпадать, и сервер отклонит такой токен.

### Зачем проверять issuer и audience?

> `Issuer` показывает, кто выпустил токен. `Audience` показывает, для какого приложения он предназначен.

### Почему `UseAuthentication` находится перед `UseAuthorization`?

> Сначала сервер должен определить пользователя, а затем проверить его права.

### Зачем нужен срок действия токена?

> Чтобы украденный или старый токен не работал бесконечно. В этом проекте токен действует один час.

### Где находится секретный ключ?

> Для разработки ключ находится в `appsettings.Development.json`. В production его нельзя хранить в репозитории — он должен передаваться через безопасную конфигурацию или хранилище секретов.

### Что можно улучшить?

> Можно подключить полный ASP.NET Core Identity, добавить блокировку после неправильных паролей, подтверждение e-mail, refresh-токены, отзыв токенов, интерфейс управления ролями и автоматические тесты безопасности.

## Завершение защиты

> В результате пользователь может зарегистрироваться и получить JWT. Сервер проверяет токен, роль и право на конкретную задачу. Без токена возвращается 401, а при недостаточных правах — 403. Пароли хранятся только в виде хеша. Дополнительно API отправляет базовые защитные HTTP-заголовки.
>
> Таким образом, в проекте реализованы три уровня: аутентификация отвечает за то, кто пользователь; авторизация определяет его права; дополнительные средства безопасности защищают ответы приложения.

## Самый короткий вариант, если времени мало

> Я добавила в TaskFlow API регистрацию и вход с JWT. Пароли сохраняются только как хеш. После входа сервер выдаёт подписанный токен на один час. Для операций используются роли `User`, `Author` и `Admin`. Кроме роли, при редактировании проверяется владелец конкретной задачи. Без токена API возвращает 401, а при недостаточных правах — 403. Также сервер добавляет CSP и другие защитные HTTP-заголовки.
