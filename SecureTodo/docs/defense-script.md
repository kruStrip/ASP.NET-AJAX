# Шпаргалка для защиты: «Безопасный Todo-менеджер»

## Перед защитой

Открыть терминал и запустить проект:

```bash
cd /home/kate/dotnet-lessons/SecureTodo
dotnet run
```

Дождаться строки:

```text
Now listening on: http://localhost:5187
```

Открыть в браузере:

```text
http://localhost:5187
```

Swagger:

```text
http://localhost:5187/swagger
```

Данные администратора:

```text
E-mail: admin@todo.com
Пароль: Admin123!
```

Также удобно заранее открыть в редакторе:

- `Program.cs` — Identity, Cookie, JWT, политики, CSRF, Swagger и security headers;
- `Models/AppUser.cs` — пользователь с полем `FullName`;
- `Models/TaskItem.cs` — модель задачи;

Если страница не открывается, проверить, что терминал с `dotnet run` продолжает работать.

## Начало рассказа

> Моя работа — это безопасный Todo-менеджер на ASP.NET Core 8. Пользователь может зарегистрироваться, войти, создавать задачи и управлять только своими задачами. Администратор может управлять всеми задачами и ролями пользователей.
>
> Для обычных веб-страниц используется Cookie-аутентификация, а для REST API используется JWT. Дополнительно реализованы CSRF- и XSS-защита, двухфакторная аутентификация, refresh-токены и защитные HTTP-заголовки.

Короткое объяснение терминов:

> Аутентификация отвечает на вопрос «кто пользователь». Авторизация отвечает на вопрос «что этому пользователю разрешено».

## 1. Регистрация через Identity

В браузере нажать **«Зарегистрироваться»**.

Ввести, например:

```text
Полное имя: Анна Иванова
E-mail: anna@example.com
Пароль: User123!
Повтор пароля: User123!
```

После регистрации пользователь автоматически попадёт на главную страницу.

Что сказать:

> В проекте используется полноценный ASP.NET Core Identity. Пароль в открытом виде в базе не хранится — Identity сохраняет только безопасный хеш.
>
> При регистрации сервер самостоятельно назначает роль `User`. Пользователь не может зарегистрировать себя администратором.
>
> После успешной регистрации выполняется автоматический вход, поэтому на главной странице сразу отображается имя пользователя.

Открыть `Pages/Account/Register.cshtml.cs` и показать:

```csharp
var result = await userManager.CreateAsync(user, Input.Password);
await userManager.AddToRoleAsync(user, "User");
await signInManager.SignInAsync(user, isPersistent: false);
```

### Проверка короткого пароля

Можно зарегистрировать другого пользователя с паролем:

```text
A1x
```

Ожидаемый результат: форма не отправляется успешно, на странице появляется ошибка.

> Минимальная длина пароля — 6 символов, и в нём обязательно должна быть цифра. Проверка выполняется на сервере, поэтому её нельзя обойти отключением JavaScript.

## 2. Вход, выход и блокировка

Открыть `Pages/Account/Login.cshtml.cs`.

> При входе `SignInManager` проверяет пароль и создаёт защищённую Identity cookie. Браузер отправляет эту cookie при следующих запросах, поэтому приложение узнаёт пользователя.

В коде показать:

```csharp
PasswordSignInAsync(
    Input.Email,
    Input.Password,
    Input.RememberMe,
    lockoutOnFailure: true);
```

> Параметр `lockoutOnFailure: true` учитывает неверные попытки. После пяти ошибок аккаунт блокируется на 15 минут.

Не проверять блокировку на `admin@todo.com`, иначе администратор временно не сможет войти. Для демонстрации использовать отдельного пользователя.

### Почему выход сделан через POST

Показать форму выхода в `Pages/Shared/_LoginPartial.cshtml`:

```html
<form method="post" asp-page="/Account/Logout">
```

> Выход изменяет состояние пользователя, поэтому он выполняется POST-запросом. Обычная ссылка с GET не должна разлогинивать пользователя.

## 3. Защита страниц и роли

Выйти из аккаунта и вручную открыть:

```text
http://localhost:5187/Tasks/Create
```

Ожидаемый результат: перенаправление на страницу входа.

> Страница создания задачи помечена атрибутом `[Authorize]`. Неавторизованный пользователь сначала должен войти.

Затем войти как обычный пользователь и открыть:

```text
http://localhost:5187/admin
```

Ожидаемый результат:

```text
403 Forbidden
```

Что сказать:

> Код 401 означает, что пользователь не определён. Код 403 означает, что пользователь определён, но у него недостаточно прав.

Войти как администратор:

```text
admin@todo.com
Admin123!
```

Открыть `/admin`. На странице должен появиться список пользователей и их роли.

> При запуске приложение идемпотентно создаёт роли `Admin`, `Author`, `User` и seed-пользователя администратора. При повторном запуске записи не дублируются.

Ожидаемый результат:


## 6. Проверка владельца задачи

Для наглядной проверки понадобятся два обычных пользователя.

1. Пользователь A создаёт задачу «Купить хлеб».
2. В другом профиле или режиме инкогнито зарегистрировать пользователя B.
3. Пользователь B открывает общий список задач.

Пользователь B увидит задачу A, но не увидит кнопки **«Редактировать»** и **«Удалить»**.

Если ID задачи равен `1`, пользователь B может вручную открыть:

```text
http://localhost:5187/Tasks/Edit/1
```

Ожидаемый результат:

```text
403 Forbidden
```

Открыть `Authorization/CanEditTaskRequirement.cs`.

> Роль определяет общий уровень доступа, а resource-based политика проверяет право на конкретную задачу.
>
> Обработчик сравнивает `TaskItem.UserId` с ID текущего пользователя. Редактировать и удалять задачу может её владелец или администратор.

Важный момент:

> Проверка выполняется не только при отображении кнопок. Сервер повторно проверяет право после прямого перехода по URL, поэтому скрытие кнопки нельзя обойти.

## 7. JWT и Swagger

Открыть:

```text
http://localhost:5187/swagger
```

Найти запрос:

```text
POST /api/auth/login
```

Нажать **Try it out** и отправить:

```json
{
  "email": "admin@todo.com",
  "password": "Admin123!"
}
```

Ожидаемый результат:

```text
200 OK
```

В ответе будут:

```json
{
  "accessToken": "...",
  "refreshToken": "...",
  "accessTokenExpiresAt": "..."
}
```

Что сказать:

> Access-токен — это JWT для доступа к API. Он содержит ID пользователя, e-mail и роли и действует 15 минут.
>
> Refresh-токен действует 7 дней и позволяет получить новую пару токенов без повторного ввода пароля.

Скопировать только значение `accessToken`. Нажать в Swagger кнопку **Authorize** и вставить токен без кавычек и без слова `Bearer`.

## 8. Проверка API без JWT и с JWT

Сначала в Swagger нажать **Logout** в окне Authorize либо открыть страницу в режиме инкогнито.

Выполнить:

```text
GET /api/tasks
```

Ожидаемый результат:

```text
401 Unauthorized
```

> Сервер не смог определить пользователя, потому что Bearer-токен отсутствует.

Теперь снова вставить JWT через **Authorize** и повторить запрос.

Ожидаемый результат:

```text
200 OK
```

> Для API-контроллера явно указана схема JWT Bearer. Cookie от веб-интерфейса не заменяет JWT для API.

## 9. Создание задачи через API

В Swagger выполнить:

```text
POST /api/tasks
```

Тело запроса:

```json
{
  "title": "Задача из Swagger",
  "description": "Создана через защищённый REST API",
  "isCompleted": false
}
```

Ожидаемый результат:

```text
201 Created
```

Обратить внимание: в теле нет `UserId`.

> Сервер берёт `UserId` из подписанного JWT. Поэтому клиент не может передать чужой ID и создать задачу от имени другого пользователя.

Обычный пользователь в `GET /api/tasks` получает только свои задачи. Администратор получает все задачи.

## 10. Refresh-токены

Открыть `SecureTodo.http` или использовать Swagger.

После `POST /api/auth/login` скопировать `refreshToken` и выполнить:

```http
POST http://localhost:5187/api/auth/refresh
Content-Type: application/json

{
  "refreshToken": "сюда_вставить_refresh_token"
}
```

Ожидаемый результат:

```text
200 OK
```

Сервер вернёт новую пару access + refresh.

Повторно отправить старый refresh-токен.

Ожидаемый результат:

```text
401 Unauthorized
```

> При обновлении используется ротация: старый refresh-токен отзывается, а клиент получает новый. Украденный старый токен повторно использовать нельзя.

Дополнительно показать:

```text
POST /api/auth/logout-all
```

> Этот endpoint отзывает все refresh-токены пользователя. Он позволяет завершить сеансы на всех устройствах.

Важное уточнение:

> В базе хранится не открытый refresh-токен, а его SHA-256-хэш. Если база утечёт, готовые refresh-токены нельзя будет просто скопировать из таблицы.

## 11. CSRF-защита

Открыть `Program.cs` и показать:

```csharp
builder.Services.AddAntiforgery(options =>
    options.HeaderName = "X-CSRF-TOKEN");

builder.Services.AddRazorPages(options =>
    options.Conventions.ConfigureFilter(
        new AutoValidateAntiforgeryTokenAttribute()));
```

Что сказать:

> Cookie браузер отправляет автоматически. Поэтому злоумышленник мог бы попытаться отправить POST-запрос от имени вошедшего пользователя с другого сайта. Antiforgery-токен доказывает, что форма была создана нашим приложением.

Формы с `method="post"` используют Razor Tag Helpers, которые автоматически добавляют скрытый токен.

### AJAX и CSRF

В списке задач нажать **«Отметить выполненной»**.

Открыть `wwwroot/js/site.js` и показать:

```javascript
headers: { "X-CSRF-TOKEN": token }
```

> Для `fetch` токен не добавляется автоматически. JavaScript читает его из `<meta name="csrftoken">` и отправляет в заголовке `X-CSRF-TOKEN`.
>
> Запрос без этого заголовка получает `400 Bad Request`.

## 12. XSS-защита

Создать задачу с описанием:

```html
<script>alert('XSS')</script>
```

Открыть список задач.

Ожидаемый результат: строка отображается как обычный текст, окно `alert` не появляется.

> Razor по умолчанию кодирует пользовательский текст. Символы `<` и `>` превращаются в безопасные HTML-сущности, поэтому браузер не выполняет введённый код.
>
> Дополнительный уровень защиты — Content Security Policy. В проекте запрещены inline-скрипты и разрешены скрипты только с нашего сайта.

## 13. Защитные HTTP-заголовки

В новом терминале выполнить, пока приложение запущено:

```bash
curl -I http://localhost:5187
```

В ответе найти:

```text
Content-Security-Policy: default-src 'self'; script-src 'self'; ...
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
Referrer-Policy: strict-origin-when-cross-origin
Strict-Transport-Security: max-age=31536000; includeSubDomains
```

Простое объяснение:

> CSP ограничивает источники скриптов и другого содержимого. `nosniff` запрещает браузеру угадывать тип файла. `DENY` запрещает открывать сайт внутри чужого iframe. `Referrer-Policy` ограничивает передачу адреса страницы. HSTS требует использовать HTTPS в production.

## 14. Двухфакторная аутентификация

Для демонстрации лучше использовать отдельного обычного пользователя, а не администратора.

1. Войти обычным пользователем.
2. Нажать **«Профиль»**.
3. Отсканировать QR-код в Google Authenticator или Microsoft Authenticator.
4. Ввести шестизначный код.
5. Нажать **«Включить 2FA»**.
6. Выйти и снова ввести e-mail и пароль.

После пароля откроется отдельная страница ввода кода.

Что сказать:

> Одного пароля теперь недостаточно. После его проверки Identity требует одноразовый код из приложения-аутентификатора.
>
> Код зависит от секретного ключа и текущего времени. Новый код создаётся примерно каждые 30 секунд.

Ввести неправильный код — появится ошибка. Ввести правильный — вход завершится.

На странице профиля также есть кнопка **«Отключить 2FA»**.

## Почему используются две схемы аутентификации

> Razor Pages удобнее использовать с Identity cookie: пользователь входит через обычную HTML-форму, и браузер сохраняет сеанс.
>
> REST API использует JWT Bearer: токен явно передаётся в заголовке `Authorization`. Это удобно для Swagger, мобильных приложений и отдельных frontend-клиентов.

Важно:

> JWT не заменяет все остальные средства безопасности. Для Razor-форм всё равно нужна CSRF-защита, пользовательский текст нужно защищать от XSS, а токены должны иметь ограниченный срок действия.

## Короткие ответы на вопросы преподавателя

### Чем 401 отличается от 403?

> 401 — пользователь не определён. 403 — пользователь определён, но у него недостаточно прав.

### Где хранится пароль?

> Открытый пароль не хранится. ASP.NET Core Identity сохраняет только его хеш.

### Почему нельзя передавать UserId при создании задачи?

> Пользователь мог бы указать чужой ID. Поэтому сервер берёт ID только из cookie или подписанного JWT.

### Зачем нужна политика CanEditTask?

> Она проверяет доступ к конкретной задаче. Владелец может изменить свою задачу, администратор — любую, остальные получают 403.

### Можно ли прочитать JWT?

> Да. JWT подписан, но обычно не зашифрован. Поэтому пароль и секретные данные в него помещать нельзя.

### Что будет, если изменить роль внутри JWT?

> Подпись перестанет совпадать, и сервер отклонит токен.

### Почему access-токен живёт только 15 минут?

> Короткий срок уменьшает последствия кражи токена. Для продолжения работы используется refresh-токен.

### Почему старый refresh-токен перестаёт работать?

> Он отзывается при ротации. Повторная отправка старого токена возвращает 401.

### Почему refresh-токен хранится как хэш?

> Чтобы его нельзя было использовать напрямую после утечки базы данных.

### Зачем нужен CSRF-токен?

> Cookie отправляется браузером автоматически. CSRF-токен подтверждает, что POST-запрос пришёл из формы нашего приложения.

### Чем CSRF отличается от XSS?

> При CSRF злоумышленник заставляет браузер отправить нежелательный запрос. При XSS он пытается внедрить JavaScript в страницу.

### Зачем UseAuthentication идёт перед UseAuthorization?

> Сначала сервер должен определить пользователя, а потом проверить его права.

### Где находится JWT-ключ?

> В учебном проекте он находится в `appsettings.json`, как требуется в задании. В production его нужно перенести в Secret Manager, переменную окружения или хранилище секретов.

### Что можно улучшить?

> Можно добавить подтверждение e-mail, восстановление пароля, резервные коды 2FA, автоматические интеграционные тесты и хранение production-секретов во внешнем защищённом хранилище.

## Завершение защиты

> В результате получился Todo-менеджер с несколькими уровнями безопасности. Identity отвечает за пользователей, пароли, Cookie, роли, блокировку и 2FA. Политика `CanEditTask` проверяет владельца каждой задачи. JWT защищает REST API, а refresh-токены позволяют безопасно обновлять короткие access-токены. Antiforgery-токены, Razor encoding, CSP и остальные HTTP-заголовки защищают веб-интерфейс.
>
> Таким образом, приложение проверяет не только личность пользователя, но и его роль, право на конкретный ресурс и безопасность каждого изменяющего запроса.
