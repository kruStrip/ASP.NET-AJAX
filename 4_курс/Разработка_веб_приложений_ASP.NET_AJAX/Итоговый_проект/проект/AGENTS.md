# AI agent instructions — МузЛото

- Source of truth: ../ТЗ/МузЛото — Единое техническое задание.docx and ../ТЗ/Требования к итоговому проекту.pdf, **amended by docs/DECISIONS.md** (it wins on conflict). Do not infer undocumented features or claim external integrations work without testing.
- Customers book through the site's own form on `/` (it replaced FormDesigner, decided 2026-10-29 evening; the FormDesigner webhook stays only for old links). After a site-form submission **no payment instructions are sent to the customer**: they see the amount, the QR image and the transfer details from `/payment-settings` (and upload a receipt) in the personal cabinet `/bookings/mine` or on `/oplata/{token}` (decided 2026-11-03, replaced the Telegram payment messages). When a receipt is uploaded, a bot posts one notification into the Telegram group topic «Подтвердить игру» (decided 2026-11-03): customer phone, customer name, amount owed, the receipt file or screenshot, and a link to the confirmation card `/bookings/pending#booking-{id}`. Replacing the receipt re-sends it. After a confirmed payment the customer gets one «Здравствуйте, мы подтвердили вашу бронь!» message with the game, date, time, location, duration, age limit, team, ticket count and total **in Telegram only** (the WhatsApp copy was switched off, decided 2026-11-03: the company does not want messages to WhatsApp), followed by a separate copy of their receipt (Wazzup cannot send text and a file together, so the text ends with «Также дублируем ваш чек.» when a receipt is attached; the file is served through a 30-day signed `/receipts/{id}/{file}?t=…` link, never a public path). If that customer confirmation is finally undeliverable (no messenger, 5 attempts used up, or the messenger stayed unconnected for 3 days), a bot posts one «Связаться с клиентом» notification into the Telegram group topic «Связаться с клиентом» with `https://t.me/…` and `https://wa.me/…` links, the phone, the full text to forward and the customer's receipt file (that text is sent as an HTML `<pre>` block with `parse_mode=HTML`, so Telegram shows a «Copy» button), so a manager can write to the customer by hand. The Telegram nickname field is back in the site form (optional; stored as `@nick`). No other automatic messaging. Customer messages go through the Wazzup cloud service (decided 2026-11-03, replaced the self-hosted WTelegramClient/WAHA setup): the company connects its WhatsApp number and Telegram account in the Wazzup web interface, the site only calls the Wazzup API. Manager notifications use the Telegram Bot API directly (`MessageChannel.TelegramBot`), not Wazzup, and are only sent to the manager group. The production server cannot reach `api.telegram.org` (Telegram is blocked for the hosting), so the bot calls go through the Cloudflare Worker relay in `deploy/cloudflare-worker` (`TELEGRAM_API_BASE_URL`, `TELEGRAM_RELAY_SECRET`); a pending receipt notification is never dropped by a payment confirmation. All messages are queued in `OutgoingMessages` in the same transaction as the booking/payment/receipt. Secrets live only in the server `.env`: `WAZZUP_API_KEY`, optional `WAZZUP_WHATSAPP_CHANNEL_ID`/`WAZZUP_TELEGRAM_CHANNEL_ID`, and `TELEGRAM_BOT_TOKEN`, `TELEGRAM_MANAGER_CHAT_ID`, optional `TELEGRAM_MANAGER_TOPIC_ID`/`TELEGRAM_CONTACT_TOPIC_ID`/`TELEGRAM_API_BASE_URL`/`TELEGRAM_RELAY_SECRET`; no messenger sessions are stored on the server. Payment details live only in the database (admin page `/payment-settings`), never in the repository.
- Pending reservations do not consume capacity. Only manual payment confirmation does. Completion deletes Pending records but preserves paid history. Capacity confirmation must remain atomic under concurrency. `/bookings/pending` («Нужно подтвердить») lists pending bookings whose customer has already uploaded a receipt (`ReceiptUploadedAt != null`, decided 2026-11-04), plus a separate «Без чека» section for imported ones (`LegacyId != null`), which can never receive a receipt because they have no site account; after a receipt is uploaded the customer sees «Чек отправлен <date>. Менеджер проверит оплату и подтвердит бронь.» instead of the payment instructions.
- Staff booking changes and cancellations also go to the manager group, queued in `OutgoingMessages` in the same transaction as the change (outbox, decided 2026-11-04): any staff edit (team, customer name, Telegram, ticket count with a refund or surcharge, surcharge confirm/cancel, restoring a cancelled booking) posts to the topic «Изменения в бронях» (`OutgoingMessageKind.BookingChanged`, `TELEGRAM_CHANGES_TOPIC_ID`), and cancelling a booking posts to «Отмена игр» (`BookingCancelled`, `TELEGRAM_CANCEL_TOPIC_ID`). Those notices carry no receipt, are HTML (`parse_mode=HTML`) with the phone in `<code>` so it is tappable to copy, and fall back to the group's General topic when their topic id is unset (they must not block); `ContactRequest` still fails without its topic. The same notices are never sent to customers, and no other automatic messaging exists.
- Customer accounts created by the site form are **temporary** (`AppUser.IsTemporaryCustomer`, login = phone): they exist only to upload the receipt and are deleted once the customer has no pending bookings left (normally right after «Подтвердить игру»). Paid bookings stay with a null `OwnerUserId`, and a new booking from the same phone creates a fresh account. Never delete permanent accounts (self-registered by e-mail, staff, Admin/Manager) and never delete an account that still has pending bookings. Customers cannot change their password: `/account/change-password` is staff-only, and an admin resets a forgotten one on `/staff`.
- Never commit customer personal data, real keys, production exports or .env files. The repository is public.
- Keep `docs/STATUS.md` up to date, distinguishing implemented from planned and verified from unverified features.
- Before treating a stage as complete, execute: `dotnet build src/MuzLoto.Web/MuzLoto.Web.csproj` and `dotnet test tests/MuzLoto.Tests/MuzLoto.Tests.csproj` (integration tests: `MUZLOTO_PG_TEST=1` and a separate test database, never `muzloto_dev`). Test concurrency against real PostgreSQL before operating live.
