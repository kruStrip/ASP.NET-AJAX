# Развёртывание: https://muzloto.b-o-c-a.ru

Приложение работает на общем сервере вместе с проектом calendar (`b-o-c-a.ru`) и не меняет его настроек.

## Как устроено

| Часть | Где | Примечание |
|---|---|---|
| Приложение | контейнер `muzloto-app-1` (образ `muzloto-web:<коммит>`), Production | память ≤ 320 МБ; ключи Data Protection и обложки — том `muzloto_appdata` (`/data`) |
| База | контейнер `muzloto-db-1`, PostgreSQL 16 | **своя**, доступна только приложению (сеть `muzloto_internal`); том `muzloto_pgdata` |
| Конфигурация | `/home/BocA/muzloto/docker-compose.yml` (из `deploy/docker-compose.prod.yml`) | |
| Секреты | `/home/BocA/muzloto/.env` (права 600) | созданы на сервере при первом развёртывании, в репозиторий не попадают |
| Прокси и HTTPS | nginx проекта calendar, файл `nginx/conf.d/muzloto.conf` (из `deploy/nginx/muzloto.conf`) | приложение подключено к сети `deploy_calendar-network` под именем `muzloto-app`; адрес разрешается при запросе, поэтому остановка МузЛото не мешает nginx |
| Сертификат | Let's Encrypt, `muzloto.b-o-c-a.ru` | продлевает контейнер `calendar-certbot` (каждые 12 ч) |
| Резервные копии | cron 03:30 → `/home/BocA/muzloto/backups/muzloto-ГГГГММДД.sql.gz`, 14 дней | |

Приложение доверяет заголовкам `X-Forwarded-*` только при `ForwardedHeaders:Enabled=true` (задано в compose):
порт контейнера не опубликован наружу, к нему ходит только nginx.

## Обновление: CI/CD

Каждый push в `main`, затрагивающий проект, запускает `.github/workflows/muzloto.yml`:

1. **build** — сборка, unit-тесты, миграции на временной PostgreSQL, интеграционные тесты, HTTP smoke.
2. **deploy** (только push в `main`, только если build зелёный, окружение `production`):
   образ собирается в Actions и публикуется в `ghcr.io/krustrip/muzloto-web:<sha>`; затем по SSH вызывается
   `deploy <sha>`. Сервер сам скачивает образ и compose-файл этого коммита, перезапускает приложение
   (миграции применяются при старте) и проверяет здоровье; **если новая версия нездорова — автоматически
   возвращает предыдущую**. Последний шаг — проверка https://muzloto.b-o-c-a.ru снаружи.

Безопасность: репозиторий публичный, поэтому
- секреты (`DEPLOY_SSH_KEY`, `DEPLOY_KNOWN_HOSTS`) лежат в окружении `production`, доступном только ветке `main`;
  pull request из форков их не получают;
- ключ деплоя отдельный и ограничен в `authorized_keys` одной командой (`restrict,command="…/ci-deploy.sh"`):
  только «развернуть образ этого коммита», без оболочки и проброса портов;
- сервер проверяет формат коммита, деплои не идут параллельно (`flock`).

Первичная настройка (один раз, владельцем репозитория): `bash scripts/setup-cd.sh`. После первого деплоя пакет
`muzloto-web` в GHCR должен быть **публичным** (как образы calendar), иначе сервер не сможет его скачать.

Ручное обновление без GitHub (запасной путь):

```bash
bash scripts/deploy.sh      # сборка образа локально, загрузка (rsync с докачкой), миграции применяются при старте
```

Первое развёртывание: `MUZLOTO_ADMIN_EMAIL=... bash scripts/deploy.sh` — создаст `.env` и покажет пароль администратора один раз.
Сервер иногда сбрасывает SSH-подключения (боты, `MaxStartups`), скрипт повторяет шаги сам.

## Мессенджеры (Telegram и WhatsApp)

После подтверждения оплаты клиенту уходит сообщение «мы подтвердили вашу бронь» (игра, дата, время, локация,
продолжительность, возраст, команда, билеты, итог), а следом — копия его чека. Отправляем только в **Telegram**
(решение заказчика 2026-11-03: копию в WhatsApp не шлём); при загруженном чеке текст заканчивается строкой
«Также дублируем ваш чек.», потому что файл приходит отдельным сообщением. Текст и файл идут двумя
сообщениями: Wazzup не умеет отправлять файл и текст одним сообщением. Чек приходит по подписанной ссылке
`/receipts/{id}/{файл}?t=…` (действует 30 дней), сам файл по-прежнему лежит вне `wwwroot`. С 2026-11-03 доставляет
облачный сервис **Wazzup**: аккаунты подключаются в его кабинете, сервер хранит только ключ API (прежние
WTelegramClient, контейнер `waha` и Cloudflare-туннель удалены).

| Переменная в `/home/BocA/muzloto/.env` | Что это |
|---|---|
| `WAZZUP_API_KEY` | ключ API: кабинет Wazzup → «Интеграция с CRM» → API → Подключить |
| `WAZZUP_WHATSAPP_CHANNEL_ID`, `WAZZUP_TELEGRAM_CHANNEL_ID` | необязательно (WhatsApp-канал сейчас не используется для клиентских сообщений): закрепить канал, если в Wazzup их несколько одного типа. Это **ID канала** (UUID вида `a1b2c3d4-…`), а не номер телефона: номер (`79247376760`) — это подключённый аккаунт, его в эти переменные не пишут. Без ID берётся единственный канал подходящего типа, а если каналов несколько — отправка ждёт, пока один не закрепят, и в ошибке перечислены их номера |
| `TELEGRAM_BOT_TOKEN` | токен бота для уведомлений менеджерам: @BotFather → `/newbot` → токен вида `123456789:AA…` |
| `TELEGRAM_MANAGER_CHAT_ID` | id группы, куда бот пишет уведомления (начинается с `-100…`); бота нужно добавить в группу |
| `TELEGRAM_MANAGER_TOPIC_ID` | необязательно: id темы «Подтвердить игру» в группе-форуме. Число из ссылки на тему (`…/123?topic=456`) — это `456` |
| `TELEGRAM_CONTACT_TOPIC_ID` | id темы «Связаться с клиентом» (туда уходит уведомление, если клиенту не удалось доставить подтверждение). Без неё такое уведомление остаётся в очереди с понятной ошибкой |
| `TELEGRAM_CHANGES_TOPIC_ID` | необязательно: id темы «Изменения в бронях» (правка заявки сотрудником: команда, клиент, Telegram, билеты, доплата, восстановление). Без неё сообщение уходит в общую тему группы |
| `TELEGRAM_CANCEL_TOPIC_ID` | необязательно: id темы «Отмена игр» (отмена одной заявки: оплата и возврат). Без неё сообщение уходит в общую тему группы |
| `TELEGRAM_API_BASE_URL` | необязательно: адрес релея Telegram Bot API (см. ниже). Пусто — сайт обращается прямо в `api.telegram.org` |
| `TELEGRAM_RELAY_SECRET` | необязательно: общий секрет релея, уходит в заголовке `X-Relay-Secret` |

Подключение (один раз, заказчиком): зарегистрироваться на app.wazzup24.ru, подключить номер WhatsApp и аккаунт
Telegram (не бота — бот не может писать клиентам первым) и отсканировать QR-коды в самом Wazzup, скопировать ключ API
в `.env`. После изменения `.env`: `cd /home/BocA/muzloto && docker compose up -d` (compose ищет `docker-compose.yml`
в текущей папке — из `/root` команда ответит «no configuration file provided»). Сообщения уходят через
`https://api.wazzup24.com/v3/message` — этот адрес с сервера доступен напрямую, туннель больше не нужен. Состояния
каналов и переписку смотрят в кабинете Wazzup; на сайте статусы отправленных сообщений видны в карточке
«Подтверждённые игры» (страница «Мессенджеры» удалена). При первом обновлении на эту версию старый контейнер `waha`
удалится сам: деплой выполняется с `--remove-orphans` (при ручном обновлении добавьте этот флаг).

### Уведомления менеджерам в Telegram

Платёжные реквизиты клиенту в Telegram больше не отправляются: после формы он попадает в личный кабинет, видит там
сумму, реквизиты и QR-код и загружает чек. Когда чек загружен, сайт отправляет в группу уведомление через **бота**:
номер клиента, имя, сумма к оплате, сам файл чека (фото или PDF) и ссылка на карточку «Подтвердить игру».

1. В Telegram создайте бота у @BotFather (`/newbot`) и добавьте его в группу менеджеров.
2. Включите в группе темы (Topics) и создайте темы «Подтвердить игру» и «Связаться с клиентом».
3. Узнайте id группы: отправьте в группу сообщение и вызовите
   `https://api.telegram.org/bot<ТОКЕН>/getUpdates` — поле `chat.id` начинается с `-100…`.
   Id темы — число в ссылке на сообщение темы (`…?topic=456` → `456`).
4. Впишите `TELEGRAM_BOT_TOKEN`, `TELEGRAM_MANAGER_CHAT_ID`, `TELEGRAM_MANAGER_TOPIC_ID` и
   `TELEGRAM_CONTACT_TOPIC_ID` в `/home/BocA/muzloto/.env` и перезапустите: `docker compose up -d`.

Если подтверждение клиенту доставить не удалось (у него нет мессенджера или все повторы исчерпаны), бот отправляет
в тему «Связаться с клиентом» отдельное сообщение: ссылки на Telegram и WhatsApp клиента, телефон и готовый текст
для пересылки, а если клиент загружал чек — сам файл чека. Так менеджер может написать клиенту вручную и
продублировать ему чек.

Без этих переменных уведомление остаётся в очереди и ничего не отправляется — ошибка видна в журнале, а данные не
теряются. Токен хранится только на сервере: в репозиторий его не коммитят.

### Если api.telegram.org недоступен (релей)

Прод-сервер не может достучаться до `api.telegram.org`: соединение по 443 висит и обрывается по таймауту (Telegram
блокируется на уровне провайдера), при этом `api.wazzup24.com` отвечает. Поэтому вызовы бота идут через маленький
Cloudflare Worker, который только пересылает запрос в Telegram (код, ограничения и пошаговая инструкция —
`deploy/cloudflare-worker/README.md`):

1. Workers & Pages → Create → Worker `muzloto-telegram-relay`, вставить содержимое
   `deploy/cloudflare-worker/worker.js`, Deploy.
2. Settings → Variables and Secrets → Secret `RELAY_SECRET` = длинная случайная строка (`openssl rand -hex 32`).
3. В `/home/BocA/muzloto/.env`: `TELEGRAM_API_BASE_URL=https://muzloto-telegram-relay.<account>.workers.dev` и
   `TELEGRAM_RELAY_SECRET=<тот же секрет>`, затем `docker compose up -d` (образ не меняется).
4. Проверка с сервера: `curl -s -H "x-relay-secret: <секрет>" "<адрес>/bot<ТОКЕН>/getMe"` → `{"ok":true,…}`.

Воркер разрешает только методы бота, которые использует сайт (`sendMessage`, `sendPhoto`, `sendDocument`,
`getMe`, `getChat`), плюс `deleteMessage` для ручной уборки отправленного по ошибке сообщения, и требует заголовок
`X-Relay-Secret` — по одному адресу воркера писать в бота нельзя.

**Файл чека через релей не загружается.** Провайдер, через которого ходит прод-сервер, пропускает к `*.workers.dev`
тела запросов только примерно до 10 КБ: POST на 68 КБ висит до таймаута, и после первых ~10 КБ уходят лишь
ретрансмиты (замерено 2026-11-03, при этом те же 68 КБ на другие узлы Cloudflare проходят). Поэтому при заданном
`TELEGRAM_API_BASE_URL` сайт отправляет в `POST {релей}/send-file` маленький JSON с подписанной ссылкой на чек
(`/receipts/{id}/{файл}?t=…`, 30 дней), а воркер скачивает файл с сайта и отдаёт его Telegram. Скачивать он может
только https с хостов из переменной `FILE_HOSTS` (по умолчанию `muzloto.b-o-c-a.ru`, можно перечислить через
запятую), файл до 20 МБ. Прямой режим без релея по-прежнему загружает файл с сервера.

После обновления кода воркера (например, если в нём появился `/send-file` или поддержка `parseMode` для HTML-подписи
с блоком `<pre>`) его нужно перезалить в панели Cloudflare: **Edit code** → вставить
`deploy/cloudflare-worker/worker.js` → **Deploy**. Пока воркер старый, уведомление о чеке
падает с ошибкой «Релей Telegram не умеет отправлять чек по ссылке — обновите deploy/cloudflare-worker/worker.js»,
а после перезаливки его достаточно вернуть в очередь: `Attempts=0`, `NextAttemptAt=now()`. Старый воркер без
`parseMode` не ломает отправку — он просто пришлёт подпись с видимыми тегами `<pre>…</pre>`; текст без чека идёт
через обычный `/bot<токен>/sendMessage`, который пересылается как есть. **На бою воркер с `parseMode` развёрнут и
проверен 2026-11-04**: `/send-file` с `parseMode: "HTML"` вернул подпись без тегов и `caption_entities` типа `pre`,
то есть у блока в Telegram есть кнопка «Copy» (`/sendMessage` с `parse_mode` тоже отдаёт `entities: [pre]`).

Уведомление о чеке не теряется, даже если оплату подтвердили раньше, чем бот успел его отправить: подтверждение
глушит только ожидающие сообщения с реквизитами. Если уведомления всё равно не приходят, смотрите
`OutgoingMessages.LastError` (там же, где статусы `Skipped`/`Failed`) и журнал:
`docker compose logs --timestamps app | grep -i telegram`.

## Откат и диагностика

```bash
ssh boca 'cd /home/BocA/muzloto && docker compose logs --tail 100 app'      # журнал
ssh boca 'cd /home/BocA/muzloto && MUZLOTO_TAG=<прежний коммит> docker compose up -d'   # откат версии
ssh boca 'gunzip -c /home/BocA/muzloto/backups/<файл>.sql.gz | docker exec -i muzloto-db-1 psql -U muzloto -d muzloto'  # восстановление (в пустую БД)
```

Отключить сайт, не трогая calendar: заменить `conf.d/muzloto.conf` на `deploy/nginx/muzloto.http.conf`
(или удалить), затем `docker exec calendar-nginx nginx -t && docker exec calendar-nginx nginx -s reload`.
Копия папки `conf.d` до подключения МузЛото: `/home/BocA/muzloto/nginx-conf.d-backup-20261029-131635`.
