# Этап 8b — заявки: количество, поиск, история

## Изменение количества билетов

| Заказ | Что происходит |
|---|---|
| Неоплаченная заявка | Количество меняется сразу (в пределах остатка мест). Места не занимаются — как и раньше. |
| Оплаченный, **меньше** билетов | Места освобождаются сразу; создаётся возврат разницы `Refund` вида «уменьшение количества» (Pending). Его отмечают в «Возвратах» после фактического перевода. Заказ остаётся оплаченным. |
| Оплаченный, **больше** билетов | Создаётся `QuantityChange` «ожидает доплаты»; места **не** занимаются. «Доплата получена» — вместимость перепроверяется в транзакции, места занимаются, платёж увеличивается. «Отменить изменение» — заказ остаётся прежним. |
| Количество 0 | Это отмена заказа (обычный путь отмены с возвратом). |

- Одновременно по заказу может ожидаться только одна доплата (уникальный индекс).
- При отмене заказа возвращается только остаток: оплата минус уже запрошенные/выполненные частичные возвраты; ожидающая доплата снимается.
- Восстановление отменённого заказа запрещено только после выполненного **возврата за отмену**; частичные возвраты ему не мешают.
- Сумма выполненных возвратов не может превысить полученную оплату.
- Подтверждённая выручка в отчёте учитывает выполненные частичные возвраты.
- Изменения — через AJAX на «Нужно подтвердить» и «Покупки» (с CSRF-заголовком); карточка и «Свободно мест на игре» обновляются без перезагрузки.
- Миграция `PaidQuantityChanges`: таблица `QuantityChanges`, `Refunds.Kind`; уникальность «один открытый/выполненный возврат на платёж» теперь только для возвратов за отмену.

## Поиск и история

- Поиск на «Нужно подтвердить», «Покупки» и «История»: команда, имя, телефон в любом формате (`8 (900) 555-12-34` найдёт `+79005551234`), первые символы ID заявки.
- `/bookings/history` — все оплаченные заказы за всё время, включая прошедшие и архивные игры: оплачено, возвращено, ожидает возврата, число изменений количества; постраничный вывод.
- Группировка повторных покупок не делалась (в ТЗ — «при необходимости»).

## Одновременная работа (исправлено)

Под SERIALIZABLE PostgreSQL отменяет одну из конфликтующих транзакций (40001). EF Core 8 оборачивает эту ошибку,
поэтому раньше она не распознавалась и давала **500**. Теперь `DbErrors` смотрит всю цепочку исключений, а операции
`BookingWorkflow` автоматически повторяются (до 5 раз): повтор видит свежие данные, поэтому при нехватке мест сотрудник
получает понятный 409, а не ошибку сервера. Сценарий 4 ТЗ («два сотрудника подтверждают последние места») покрыт тестом:
20 раундов параллельных подтверждений, перепродажи нет.

## Проверка

58 тестов, стабильно в нескольких прогонах подряд. Внешний вид «Покупок» с ожиданием доплаты и её подтверждением проверен в браузере.
