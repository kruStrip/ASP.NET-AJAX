# Этап 5 — сотрудники, роли и назначения

## Добавлено

- `/staff`: администратор создаёт учетную запись с именем, e-mail, временным паролем (от 12 символов), ролью Admin/Manager/User. Повторный e-mail запрещён, ошибки Identity показываются в интерфейсе. Пароль сохраняется только как хеш через ASP.NET Core Identity.
- `/staff`: администратор меняет роль существующего сотрудника. Собственную роль менять нельзя; удаление последнего администратора запрещено. При смене с Manager на другую роль все назначения удаляются.
- `/staff/assignments/{sessionId}`: администратор назначает менеджеров на отдельные игры или отзывают назначение. Назначить User или Admin в качестве Manager нельзя.
- `/account/change-password`: любой авторизованный сотрудник меняет собственный пароль.
- **Текущая авторизация:** страницы и API для Manager уже фильтруются по `EventStaffAssignment`; права теперь можно выдавать через интерфейс. При смене роли SecurityStamp обновляется; cookies проверяют SecurityStamp на запросах, JWT содержит stamp и при каждом запросе сверяет его и текущие роли с Identity.

## Правила доступа

| Роль | Администраторская часть | Игры и заявки | Финансы/возвраты |
|---|---|---|---|
| Admin | создание сотрудников, роли и назначения | все игры | все отчёты/возвраты |
| Manager | нет | только назначенные игры | только показатели своего dashboard (глобальные отчёты закрыты) |
| User | нет | нет | нет |

## Ручная проверка

1. Администратором создать тестового Manager с уникальными почтой и временным паролем. Пароль не записывать в репозиторий.
2. Выйти, войти под Manager: без назначений не должны показываться чужие игры, заявки и покупки; `/staff` должен отвечать запретом.
3. Войти администратором, открыть «Игры» → «Сотрудники игры», назначить Manager на одну игру.
4. Войти менеджером: только эта игра и её заявки доступны; попытка управления другой игрой запрещена на сервере.
5. Отозвать назначение и проверить, что чужая игра исчезла после обновления менеджером страницы.
6. Изменить роль Manager → User: назначения удалятся, старые cookie и JWT станут недействительны после повторной проверки.
7. Проверить смену пароля через `/account/change-password`; повторный вход со старым паролем должен быть запрещён.

## Ограничения

- Отправка приглашений и временных паролей по e-mail отсутствует: администратор передаёт пароль по защищённому каналу. Для реального использования нужны аудит административных операций, управление деактивацией аккаунтов и принудительный сброс временных паролей.
- **SignalR:** доступ к группам проверяется при JoinSession. Если менеджеру отозвали назначение во время активного WebSocket-соединения, уже существующее членство в группе не отзывается до переподключения. Текущие уведомления включают только идентификаторы, не персональные данные; для production требуется управляемое отключение существующих соединений или повторная авторизация уведомлений.
- Схема PostgreSQL **не меняется**: AppUser.FullName и EventStaffAssignment уже были созданы в прежних миграциях.
- Перед реальной эксплуатацией нужна проверка GitHub Actions и работающего интерфейса.
