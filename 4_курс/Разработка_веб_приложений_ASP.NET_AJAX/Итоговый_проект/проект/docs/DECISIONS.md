# Изменения согласованных решений

Документ фиксирует решения, которые **меняют** исходное ТЗ (`../ТЗ/МузЛото — Единое техническое задание.docx`).
При расхождении действует этот файл. Бизнес-правила по местам не меняются: заявка не занимает места до
ручного подтверждения оплаты, при завершении игры неоплаченные заявки удаляются, оплаченная история сохраняется.

| Дата | Решение | Было в ТЗ | Статус |
|---|---|---|---|
| 2026-10-28 | Собственная публичная форма бронирования `/book` заменяет FormDesigner. Адаптер FormDesigner остаётся отключаемым на период перехода. | FormDesigner сохраняется, своя клиентская форма не создаётся | запланировано (этап 6b) |
| 2026-10-28 | Автоматические сервисные сообщения клиенту через **отдельный рабочий Telegram-аккаунт** компании (MTProto-клиент, не бот): бот не может написать первым. Только с согласия клиента в форме, очередь без дублей, ограничение частоты. Данные аккаунта и сессия — только в секретах сервера, не в репозитории. | Канал уведомлений сохраняется прежним, рассылки вне рамок | запланировано (этап 7) |
| 2026-10-28 | Скриншот или файл перевода от клиента прикладывается к заявке и предварительно распознаётся (сумма, дата, получатель). **Окончательное подтверждение оплаты остаётся за сотрудником**: скриншот легко подделать. Полная автоматизация — только по данным банка (выписка/API), если банк компании это поддерживает. | Только ручное подтверждение | на уточнении |
| 2026-10-28 | У роли User есть собственные ресурсы: `Booking.OwnerUserId`. Заявки, созданные под учётной записью, видны владельцу в `/bookings/mine` и через API (этап 7). | User — демонстрационная роль без описания ресурса | реализовано (этап 6a) |
