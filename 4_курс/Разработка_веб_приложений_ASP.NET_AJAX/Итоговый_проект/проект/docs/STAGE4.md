# Этап 4 — возвраты денежных средств (контроль сотрудником)

## Бизнес-правила

1. Отмена неоплаченной заявки не создаёт возврат.
2. Отмена подтверждённого оплаченного заказа **сразу освобождает билеты**, но **не меняет сумму реально возвращённых денег**. В таблицу `Refunds` записывается запрос со статусом `Pending` на полную сумму подтверждённого `Payment`.
3. Только администратор может подтвердить фактическое перечисление в `/refunds` после внешнего перевода денег клиенту. Платёжная интеграция не выполняется автоматически.
4. После подтверждения `RefundStatus.Completed` сумма учитывается в возвращённых деньгах. Чистые поступления = подтверждённые платежи минус подтверждённые возвраты.
5. Восстановление в течение часа разрешается **только до фактического возврата денег**. Оно отменяет запрос со статусом `Pending`, сохраняет изначальный платёж и повторно резервирует билеты при достаточной вместимости.
6. После `Completed` восстановление запрещено даже в пределах часа. Для нового бронирования требуется новая заявка и новая оплата.
7. История возвратов хранится в БД. Для финансовых данных отмена запроса не означает удаления записи. Стадии: `Pending`, `Completed`, `Cancelled`.
8. Полный возврат предусмотрен в текущей версии. Частичные возвраты, комиссии и автоматические платёжные провайдеры НЕ реализованы.

## Развёртывание на существующей БД

**Перед обновлением:** сохрани резервную копию базы, останови работающий процесс `bash scripts/dev.sh` и убедись, что нет несохранённых изменений.

Из каталога проекта после распаковки ZIP:

```bash
bash scripts/init-db.sh  # Создаёт миграцию RefundWorkflow и применяет схему
bash scripts/dev.sh
```

Созданные EF Core файлы `*_RefundWorkflow.cs`, `*_RefundWorkflow.Designer.cs`, `AppDbContextModelSnapshot.cs` нужно добавить и закоммитить.

**Не запускай приложение с новой моделью до миграции.** GitHub Actions также создаёт временную миграцию `RefundWorkflow` и тестирует её на отдельной БД.

## Ручная проверка

- В `/bookings` отмени ранее оплаченную покупку (используй только тестовые данные).
- В `/refunds` найди запись `Pending`: отчёт должен сохранить валовые поступления, а количество действующих билетов уменьшиться.
- Если деньги НЕ переведены, открой `/bookings/cancelled`, восстанови покупку в течение часа: запрос должен стать `Cancelled` и исчезнуть из ожидающих возвратов.
- Снова отмени, в `/refunds` подтверди реально выполненный **тестовый** перевод (без реальных денег). Отчёт должен показать сумму в «Возвращено клиентам» и скорректировать «Чистые поступления».
- Убедись, что после завершённого возврата восстановить заказ нельзя. Повторное подтверждение того же возврата не должно изменять данные.

## Существующие отменённые покупки

У заказов, отменённых **до обновления**, таблица Refunds будет пуста. Не создавайте для них автоматические возвраты задним числом: могли уже вернуть деньги вне системы. Сначала сверьте старые отмены и переводы вручную.

## Ограничения

Не использовать запись «Деньги возвращены» вместо фактического перевода. Платежи не выполняются программой; подтверждение — ручная отметка. Для production необходим аудит полномочий, документальное подтверждение переводов, защита персональных данных, сверка с банком и реальные интеграционные тесты.
