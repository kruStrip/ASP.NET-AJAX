# МузЛото — этап 2: API, AJAX, SignalR, PostgreSQL

Статус: исходники подготовлены. Сборка этапа 1 успешно прошла CI. **Этап 2 требует нового успешного CI, генерации миграций и проверки пользовательских сценариев** — не считать релизом.

## Функциональность

- `POST /api/auth/token` (с этапа 6a основной адрес — `/api/auth/login`): выдача JWT через `SignInManager.CheckPasswordSignInAsync`, только сотрудникам Admin/Manager; cookie для Razor Pages остаются отдельными.
- CRUD `api/v1/sessions` и `api/v2/sessions`: отдельные DTO. V1 — `capacity`, `reserved`, `venue`; V2 — объекты `location`, `seats` на входе и `availability`/`status` на выходе; поиск/постраничность.
- Доступ: Admin создаёт, изменяет, удаляет; Manager читает только назначенные ему сеансы. Удаление при наличии заявок запрещено.
- Обновления через AJAX на страницах: подтверждение, отмена, завершение сеанса. Прогрессивные POST-формы с обычной подачей при отключённом JavaScript, antiforgery и обработка 401/403/409.
- SignalR browser client (из локального npm-пакета). Подписывается на разрешённые сеансы и обновляет видимые списки после серверных событий.

## Первый запуск PostgreSQL и миграций

Требования: Docker Compose, .NET 8 SDK, Node.js/npm (только для SignalR-клиента).

```bash
cp .env.example .env
# Заменить REPLACE_... на длинные случайные пароли и секреты.
docker compose up -d postgres
bash scripts/init-db.sh
bash scripts/install-client.sh
bash scripts/dev.sh
```

**Важно:** `scripts/init-db.sh` создаёт `InitialCreate` из текущей EF Core модели (если файла ещё нет), затем применяет миграции. После проверки обязательно сохраните миграции в Git:

```bash
git add '4_курс/Разработка_веб_приложений_ASP.NET_AJAX/Итоговый_проект/проект/src/MuzLoto.Web/Data/Migrations/'
git commit -m 'db(muzloto): track initial PostgreSQL migrations'
git push
```

GitHub Actions использует временный PostgreSQL 16, генерирует или применяет схему, проверяет реальную бизнес-логику бронирований (Pending, Confirmed, переполнение, завершение), запускает приложение и проверяет HTTP/JWT-сценарии и наличие браузерного клиента SignalR. Из workflow можно скачать `muzloto-ef-migrations` и сохранить его содержимое в проекте, если SDK на локальном компьютере недоступен. Миграции от CI нужно проверять перед применением на реальных данных.

## JWT

Получить access-токен (нужен созданный администратор и реальные локальные пароли):

```bash
curl -X POST http://localhost:5080/api/auth/token \
  -H 'Content-Type: application/json' \
  -d '{"email":"admin@example.test","password":"YOUR_DEV_PASSWORD"}'
```

Далее `Authorization: Bearer <accessToken>`. Без JWT запросы к `/api/v1/sessions` и `/api/v2/sessions` должны возвращать 401. Пользователь Manager видит только привязанные сеансы и не может создавать или изменять их (403).

## Что НЕ готово

- Настоящее подключение FormDesigner: необходимо проверить формат полей, защиту вебхуков, идентификаторы и окружение поставщика; текущий endpoint — внутренний JSON-адаптер.
- Сквозные интеграционные тесты оплаты с конкурентными запросами и откатами.
- Контракт API создания игр (CRUD v1/v2 относится к сеансам; игры создаются в интерфейсе).
- Аудит секретов и юридические требования для реальных клиентских данных.
- Продакшен-развёртывание, нагрузочные тесты, отказоустойчивость SignalR.

## Безопасность

Не переносить данные действующих клиентов в публичный учебный репозиторий. Не коммитить `.env` и `Jwt__Key`. На production используйте HTTPS, Secure cookie, ротацию ключей, ограничение скорости на входе и проверенную авторизацию подписок в SignalR.
